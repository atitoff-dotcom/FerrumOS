    🧭 Roadmap: CAN-шина в FerrumOS — Распределенные сигналы, автономность и полевое обслуживание¶

    Этот документ фиксирует архитектурный план и спецификацию интеграции шины CAN (TWAI / CAN 2.0B) в экосистему FerrumOS: распределенные реактивные сигналы, заливка байткода по проводу (FRP over CAN), режим энергосбережения «холодный чип» и сценарий полевого обновления ядра с мобильного телефона.

    🎯 Ключевые цели и философия¶

    1. Автономность без единой точки отказа (No Single Point of Failure):
    2. Критическая автоматика (свет, реле, аварийные краны, насосы) работает на физическом уровне шины CAN.
    3. Выключатель и лампа реагируют за 0.2 миллисекунды даже при отключенном роутере, зависшем Home Assistant или обесточенном сервере.
    4. Отказ от «тупых экспандеров портов» в пользу автономных узлов:
    5. Каждый узел на шине — полноценный микроконтроллер ESP32-C6 со своей локальной логикой, аппаратными фильтрами антидребезга и защитой.
    6. Пины всегда локальны. Узлы общаются исключительно через распределенные сигналы.
    7. «Холодный чип» и чистый радиоэфир:
    8. На ведомых CAN-модулях радиомодем Wi-Fi по умолчанию выключен (WiFi.mode(OFF)).
    9. Потребление чипа снижается до 15–20 мА, температура падает до 30°C (вместо 55°C), устраняются радиопомехи в спальнях и металлических щитах.
    10. Компилятор считает ID сам (Zero Magic Numbers):
    11. Пользователь не пишет магические hex-числа вида .can(0x101).
    12. 29-битный расширенный CAN ID автоматически рассчитывается компилятором из имени сигнала ("living/light").

    📐 Спецификация Modern Human-JS¶

    1. Настройка шины на узле:¶

    // Атомарная инициализация CAN-контроллера TWAI:
CAN.bus()
    .pins({ tx: 21, rx: 22 })
    .baud(250000);

    2. Модуль выключателя (Публикация сигнала):¶

    // Объявляем сигнал и отправляем его в CAN-шину:
let light = state.signal("living/light", false).can();

const btn = GPIO.input(4).pullUp().debounce(25);
btn.onClick(() => {
    light = !light; // Мгновенный 1-байтовый CAN-кадр в шину
});

    3. Модуль в силовом щитке (Подписка на сигнал):¶

    // Слушаем тот же сигнал из CAN-шины:
let light = state.signal("living/light", false).can();
const relay = GPIO.output(15).initial(false);

light.watch((on) => {
    relay.write(on); // Срабатывание за 0.2 мс
});

    4. Шлюз в Home Assistant:¶

    // Шлюз слушает CAN и транслирует состояние в Home Assistant:
let light = state.signal("living/light", false)
    .can()
    .exposeHA("switch", { name: "Люстра в гостиной" });

    5. Аварийные сигналы с приоритетом арбитража CAN:¶

    // Аварийный сигнал с наивысшим приоритетом в шине:
let leak = state.signal("bath/leak", false).can().urgent();

    🧬 29-битная иерархия CAN ID и аппаратная фильтрация (Hardware Acceptance Mask)¶

    Для устранения нагрузки на процессор и предотвращения «захлебывания» узлов на общей шине расширенный 29-битный CAN ID структурируется компилятором как иерархический вектор:

     28      26 25          16 15                           0
┌──────────┬──────────────┬──────────────────────────────┐
│ Priority │  Subnet /    │      Signal Hash (CRC16)     │
│ (3 bits) │ Area ID (10) │      (16 bits, Murmur3)      │
└──────────┴──────────────┴──────────────────────────────┘
    1. Биты приоритета [28..26] (3 бита):
    2. 000 — Критические аварии / Безопасность (протечка, пожар, аварийный STOP). Побеждают любой трафик в физическом арбитраже шины за 0 нс.
    3. 001 — Оперативное управление в реальном времени (кнопки, выключатели, реле).
    4. 010 — Стандартные распределенные сигналы (термостаты, таймеры).
    5. 011 — Потоковая телеметрия (температура, мощность, диагностика).

    6. 100..111 — Системный транспорт (FRP over CAN, ISO-TP Broadcast OTA).

    7. Префикс зоны Subnet / Area ID [25..16] (10 бит):

    8. Идентифицирует логический шкаф, этаж или сегмент автоматики (до 1024 зон).

    9. Позволяет локализовать трафик: сигналы кухни не будят контроллеры котельной.

    10. Хэш сигнала Signal Hash [15..0] (16 бит):

    11. Детерминированный 16-битный хэш имени сигнала (например, Murmur3("living/light")).

    Аппаратный отсев в кремнии (Zero CPU Overhead)¶

    Контроллеры ESP32-C6 (TWAI) и CH32V307 содержат аппаратные компараторы Acceptance Filter (AMR / ACR): - Регистр фильтра настраивается на маску Subnet ID узла. - Пакеты чужих зон отбрасываются напрямую в кремнии контроллера за 0 процессорных тактов, не вызывая аппаратного прерывания и сохраняя ядро в глубоком сне.

    🌸 Программный Bloom-фильтр подписок и Generation Counter¶

    Если узел подключен к шине с десятками сигналов одной зоны:

    1. 64-битный Bloom-фильтр в прерывании (2 такта CPU)¶

    При компиляции скрипта ядро строит 64-битную битовую маску всех активных подписок Signal.on(): 

    // При регистрации подписки:
bloom_mask |= (1u64 << (hash1 % 64)) | (1u64 << (hash2 % 64));
    При получении кадра драйвер в ISR выполняет элементарную битовую проверку: 
    let tag = (1u64 << (frame_hash % 64));
if (bloom_mask & tag) != tag {
    return; // Чужой сигнал: мгновенный возврат из ISR без аллокаций памяти!
}

    2. Generation Counter (Эпохи без NTP)¶

    Каждый узел-источник поддерживает монотонный 16-битный счетчик поколений epoch_seq: - Узел-приемник отбрасывает пакеты с seq <= last_seen_seq. - Это обеспечивает абсолютную защиту от повторных пакетов (Replay Attack) и коллизий при переподключении шины без тяжелых сетевых протоколов времени (NTP).

    ⚡ FRP over CAN (Заливка задач по витой паре)¶

    Для заливки сценариев не требуется Wi-Fi на каждом модуле: 1. Studio шлет байткод на Шлюз по TCP/HTTP. 2. Шлюз нарезает байткод (30–150 байт) на CAN-кадры протокола FRP. 3. Время передачи 100 байт на скорости 250 кбит/с составляет всего ~5 мс. 4. Целевой модуль принимает байткод, проверяет CRC16 и выполняет Zero-Downtime Hot-Swap на лету.

    📱 Полевое обслуживание без интернета («Подошел с телефоном»)¶

    Сценарий для объектов без Wi-Fi (дачи, подземные паркинги, насосные станции):

    Шаг 1. Физическая активация (Защита от взлома по радио)¶

    • Инженер подходит к модулю и удерживает сервисную кнопку 5 секунд (или нажимает 5 быстрых кликов).
    • Модуль кратковременно пробуждает Wi-Fi радиомодем в сервисный режим.

    Шаг 2. Скачивание ядра с телефона¶

    • Вариант А (Hotspot): Модуль подключается к заранее настроенной точке доступа смартфона (Ferrum-Service) и сам забирает свежий релиз.
    • Вариант Б (SoftAP): Модуль раздает Wi-Fi FerrumOS-Setup. Инженер открывает браузер на телефоне и загружает файл прошивки через мобильный веб-интерфейс.

    Шаг 3. Каскадная раздача по CAN (P2P Mesh Update)¶

    • Обновленный модуль выступает «донором» и передает бинарник по витой паре CAN соседним узлам.
    • Весь дом обновляется за один визит, даже если сотовая связь ловит только у входной двери.

    🔌 Режим Single-Wire Open-Drain CAN (25 кбит/с, Zero-Transceiver)¶

    Для коротких линий (внутри щитка, на DIN-рейке между соседними автоматами или модулями) дифференциальный трансивер исключается для экономии места и себестоимости:

    Схемотехника и физический уровень:¶

    1. Прямой Open-Drain без диодов:
    2. Пин TWAI_TX настраивается в режиме прямого открытого стока (Open-Drain).
    3. Вход TWAI_RX через внутреннюю матрицу GPIO Matrix ESP32-C6 заводится на тот же самый физический пин (1 пин на узел).
    4. Прямой полевик дает $V_{OL} pprox 0.03 ext{ В}$ (настоящий твердый ноль без диодного падения $0.3 ext{ В}$), обеспечивая идеальную помехозащищенность.
    5. Один резистор подтяжки на шину:
    6. Вся шина подтягивается к 3.3V одним резистором $2.2 ext{–}3.3 ext{ кОм}$.
    7. Скорость 25 кбит/с:
    8. Идеальные фронты нарастания через резистивную подтяжку без завалов емкостью проводов.
    9. 1 CAN-кадр передается за ~4 миллисекунды (мгновенный отклик для выключателей и реле).
    10. Байткод сценария (100 байт) заливается за 0.3–0.4 секунды.

    Примеры кода:¶

    Сценарий для Модуля 1 (Выключатель на стене):¶

    // 1. Инициализация однопроводной шины CAN на GPIO 21 (25 кбит/с):
CAN.bus().singleWire(21).baud(25000);

// 2. Распределенный сигнал света:
let light = state.signal("living/light", false).can();

// 3. Физическая клавиша выключателя с антидребезгом:
const btn = GPIO.input(4).pullUp().debounce(25);

btn.onClick(() => {
    light = !light; // Мгновенная отправка 1-байтового CAN-кадра
});

    Сценарий для Модуля 2 (Силовой щиток с реле):¶

    // 1. Инициализация однопроводной шины CAN на GPIO 21 (25 кбит/с):
CAN.bus().singleWire(21).baud(25000);

// 2. Подписка на тот же самый распределенный сигнал:
let light = state.signal("living/light", false).can();

// 3. Локальное силовое реле люстры:
const relay = GPIO.output(15).initial(false);

// 4. Реактивный слушатель (срабатывает за 0.2 мс при приходе кадра):
light.watch((on) => {
    relay.write(on);
});

    🔵 Bluetooth 5 (BLE WebBluetooth) для смены ядра со смартфона¶

    ESP32-C6 аппаратно оснащен радиомодулем Bluetooth 5 (LE) с поддержкой высокоскоростного физического уровня 2M PHY (до 2 Мбит/с). Использование BLE для сервисного обслуживания превосходит Wi-Fi по удобству:

    Преимущества BLE перед Wi-Fi SoftAP:¶

    1. Без разрыва интернета на телефоне: Смартфон остается на связи по 4G/5G, может на лету скачать свежий релиз прошивки и одновременно передавать его по BLE на ESP32-C6.
    2. WebBluetooth прямо из браузера (Zero-Install): Не требуется ставить отдельные Android/iOS приложения. Прошивка идет прямо из браузера (Chrome, Edge) через стандартный WebBluetooth API.
    3. Скорость 2M PHY: Реальная пропускная способность BLE 5 на ESP32-C6 достигает 100–130 КБ/с. Бинарный образ ядра Rust (400–500 КБ) пролетает всего за 3–5 секунд.
    4. Сценарий работы:
    5. На модуле зажимается сервисная кнопка (5 сек).
    6. Модуль выдает BLE-рекламу Ferrum-OTA.
    7. В браузере смартфона нажимается кнопка «Подключить» в шторке WebBluetooth.
    8. Прошивка заливается в OTA-раздел Flash-памяти.
    9. Модуль перезагружается в новое ядро, BLE выключается, управление возвращается в CAN.

    ⚡ Синхронная параллельная прошивка ядер (Broadcast Dual-Bank OTA) на базе ISO-TP¶

    Поскольку шина CAN физически является широковещательной средой (Broadcast), а все модули построены на единой архитектуре ESP32-C6 RISC-V:

    1. Параллельное обновление флота за единое время $O(1)$:¶

    • Шлюз или смартфон передает поток блоков прошивки широковещательным CAN-кадром.
    • Все узлы на шине одновременно слушают шину и параллельно записывают блоки во второй (неактивный) банк Flash (ota_1).
    • Время обновления 50 узлов равно времени обновления одного узла (нет линейного роста времени $N imes T$).
    • Активный банк ota_0 продолжает работу вплоть до финальной команды перезапуска (100% Anti-Brick защита).

    2. Применение автомобильного стандарта ISO-TP (ISO 15765-2):¶

    Для нарезки, контроля последовательности и предотвращения переполнения Flash-памяти используется транспорт ISO-TP:

    1. Кадры Consecutive Frame (CF) со счетчиками Sequence Number (SN):
    2. Каждый пакет данных содержит 4-битный счетчик SN (от 0 до 15).
    3. Мгновенное обнаружение сбоя на лету: если модуль ожидал кадр с SN=2, а прилетел SN=3, он мгновенно (за 4 мс) фиксирует потерю конкретного фрагмента, не дожидаясь конца всей прошивки.
    4. Защита от переполнения буферов Flash (STmin Pacing):
    5. Стирание сектора 4 КБ во Flash занимает 10–20 мс.
    6. Передатчик соблюдает интервал разделения кадров STmin (Separation Time = 1–2 мс), гарантируя, что даже самый медленный чип успевает сбрасывать данные во Flash-буфер.

    3. Решение коллизий: Пакетная битовая карта (Batching Bitmask) и выборочный дозапрос:¶

    Что происходит, если из 16 модулей 15 приняли блок идеально, а 16-й получил ошибку: - Никаких перебиваний в процессе: пока идет передача стрима (блока 4 КБ), все узлы молчат. Приемники ведут в RAM крошечную битовую маску (64 байта на весь файл). - Фаза проверки (Check Phase): по окончании блока шлюз запрашивает статус. Узел №16 отправляет короткий адресный кадр ISO-TP NACK: [NACK: Block #X, Missing SN #2]. - Идемпотентность и защита Flash: шлюз повторяет недостающий фрагмент в шину. Узел №16 дописывает его, а остальные 15 узлов сверяются со своей битовой маской («у нас этот фрагмент уже записан») и игнорируют дубликат, сберегая ресурс циклов перезаписи Flash. - Синхронный коммит: когда все узлы подтверждают совпадение SHA-256 хэша, шлюз отправляет широковещательную команду OTA_COMMIT_AND_REBOOT, и весь флот одновременно переключается на новое ядро.

    4. Расчет реального времени прошивки на шине 25 кбит/с:¶

    Физическая пропускная способность при скорости 25 кбит/с: - По проводу передается 25 000 импульсов в секунду. - С учетом 29-битных заголовков CAN, бит-стаффинга, контрольных сумм CRC и нарезки ISO-TP реальная эффективная скорость составляет ~1.1–1.2 КБ/с (чистый полезный поток данных).

    Ключевые преимущества: 1. Время O(1) для всего флота: Благодаря широковещательной трансляции (Broadcast), 20 или 50 модулей в щитке обновляются за те же самые 2.5 минуты, что и один модуль (время не масштабируется линейно). 2. Zero-Downtime при прошивке ядер: Все 2.5 минуты модули продолжают управлять светом и реле из активного Банка 1. Переключение происходит мгновенно после верификации SHA-256. 3. Экспресс-альтернатива по BLE: Если требуется экстренное обновление конкретного узла за секунды — через Bluetooth 5 (BLE 2M PHY) то же ядро прошивается со смартфона всего за 3.5 секунды.
