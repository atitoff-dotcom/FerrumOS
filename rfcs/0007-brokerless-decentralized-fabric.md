## 🎯 1. Введение и Проблематика

### 1.1. Критическая уязвимость централизованных брокеров (MQTT)
В современной любительской автоматизации (Home Assistant, Zigbee2MQTT, ESPHome) де-факто стандартом стал протокол **MQTT с центральным брокером** (Mosquitto, EMQX). 

Это создает **критическую единую точку отказа (Single Point of Failure)**:
1. **Катастрофический сбой при падении брокера**: Если сервер с Mosquitto зависает, перезагружается, сталкивается с нехваткой памяти или сбоем SD-карты — **вся автоматизация в доме мгновенно умирает**. Выключатель в коридоре не может включить реле в щитке, даже если оба микроконтроллера физически исправны и включены.
2. **Задержка «ватного отклика» (Latency Stack)**: Путь команды от датчика до реле проходит через стек: `Датчик -> Wi-Fi -> IP-стек -> TCP Handshake -> MQTT Broker (диск/очереди) -> Home Assistant (Python Event Loop) -> MQTT Broker -> TCP -> Wi-Fi -> Реле`. Суммарная задержка составляет 300–800 мс.
3. **Зависимость от бытового Wi-Fi роутера**: Подвисание домашнего роутера или смена пароля Wi-Fi парализует управление освещением и отоплением.

### 1.2. Философия FerrumOS: Edge-First & Zero-Broker
В FerrumOS реализован принцип **полной децентрализации (Brokerless Fabric)**:
* Микроконтроллеры общаются **напрямую чип-в-чип (Peer-to-Peer)**.
* Сервер FerrumHub и мобильные дашборды являются **наблюдателями и координаторами верхнего уровня**, но не посредниками в контуре прямого управления.
* Если сервер физически отключен или уничтожен — **100% сценариев, кнопок, климат-контроля и защиты от протечек продолжают работать автономно**.

## 🏛️ 2. Архитектура распределенной фабрики сигналов

Связь между узлами организуется через три физических децентрализованных транспорта:

│            │                                                           │                 │

## 📡 3. Детализация транспортных уровней

### 3.1. Беспроводной транспорт: Thread (IEEE 802.15.4)
* **Аппаратная база**: Радиомодуль ESP32-C6 / BL702 с поддержкой 802.15.4.
* **Топология Mesh**:
  * Каждое устройство с постоянным питанием (реле, диммер) выступает как **Thread Router**, расширяя зону покрытия сети.
  * Батарейные датчики работают в режиме **Sleepy End Device (SED)** с током покоя ~1.8 мкА.
* **Самоисцеление (Self-Healing)**:
  * В сети Thread нет единого координатора (в отличие от старого Zigbee, где гибель координатора ломает сеть).
  * Роль лидера динамически переизбирается за 2–3 секунды любым доступным роутером.
* **Прямая маршрутизация**:
  * Пакет `CoAP POST coap://[fdde:...]/sig/hall/toggle` летит напрямую от выключателя к реле через соседние роутеры без участия внешнего сервера.

### 3.2. Проводной транспорт: CAN-шина (TWAI)
* **Аппаратная база**: ESP32-C6, CH32V307, изолированные трансиверы SN65HVD230 / TJA1051.
* **Принцип Multi-Master**:
  * Любой узел имеет право начать передачу в любой момент.
  * Физический побитовый арбитраж по идентификатору CAN ID: сообщения с высоким приоритетом (аварийная кнопка, протечка) передаются без задержки, вытесняя телеметрию температуры.
* **Абсолютная надежность**:
  * Короткое замыкание или отключение питания одного узла изолируется драйвером (Bus-Off State) и не нарушает связь остальных устройств на шине.

### 3.3. Локальный Wi-Fi/Ethernet: UDP Multicast & FRP
* **Адрес группы**: `239.255.42.42:5005`.
* **Бинарный формат кадра Signal Frame (20 байт, 0 аллокаций)**:
  ```text
  [0..1]   Magic Header (0xFE 0x05)
  [2]      Version (0x01)
  [3]      MsgType (0x10 = SIGNAL_EMIT, 0x20 = STATE_SYNC_LWW)
  [4..7]   Signal / Topic Hash (CRC32 от "living/light_toggle")
  [8..11]  Signal Value (i32 / f32)
  [12..15] Sequence / Epoch Counter (монотонный счетчик генерации)
  [16..17] Origin Node ID (u16)
  [18..19] Bloom Filter Tag (16-битный хеш-отпечаток для ISR-отсева)
  ```
* **Аппаратный и Bloom-фильтр отсев**:
  1. На аппаратном уровне Wi-Fi/Ethernet MAC-фильтр отсекает посторонние широковещательные пакеты.
  2. В обработчике сокета драйвер проверяет поле `Bloom Filter Tag` по 64-битной маске подписок узла за 2 такта CPU:
     ```rust
     if (local_bloom_mask & packet.bloom_tag) != packet.bloom_tag {
         return; // Мгновенный сброс чужого сигнала без чтения в VM
     }
     ```

### 3.4. Бесконфликтная репликация состояния: CRDT (LWW-Register)
Для синхронизации состояний (положение штор, уставка термостата, статус контакторов) без центральной базы данных и тяжелых консенсусов (Raft):
* **Структура регистра LWW (Last-Write-Wins)**:
  Каждое состояние хранится как кортеж `(value, epoch, origin_node_id)`.
* **Автоматическая сходимость при разделении сети (Network Partition)**:
  Если сегмент сети был изолирован, при восстановлении связи узлы обмениваются своими LWW-регистрами (`MsgType = 0x20`). Побеждает запись с наибольшим `epoch` (при равенстве — с наименьшим `origin_node_id`). Сходимость математически гарантирована за $O(1)$ раундов обмена.

### 3.5. Пограничные шлюзы и интеграция со SCADA через Zenoh-Pico
Для связи локальной беспорочной фабрики (CAN / Thread / UDP) с верхним уровнем (FerrumHub, мобильные приложения, SCADA):
* Пограничные узлы с Ethernet запускают микростек **Zenoh-Pico** (написан на Rust, footprint < 50 КБ).
* Zenoh связывает распределенные Fabric-сегменты цехов и этажей по протоколу P2P без необходимости разворачивать сервер MQTT, обеспечивая маршрутизацию Pub/Sub/Query на уровне здания.

## 💻 4. Программный интерфейс Fluent JS

Разработчик автоматизации не думает о физическом носителе (Thread, CAN или Wi-Fi). Ядро виртуальной машины маршрутизирует сигнал автоматически во все активные интерфейсы.

### 4.1. Генерация сигнала (Датчик / Выключатель):
```javascript
const button = GPIO.input(4)
    .pullUp()
    .debounce(50);

button.onClick(() => {
    // Автоматически отправляется в Thread Mesh, CAN и UDP Multicast
    Signal.emit("living/light_toggle");
});
```

### 4.2. Прием сигнала (Исполнительное реле):
```javascript
const chandelier = GPIO.output(15)
    .initial(false);

// Подписка на распределенный сигнал:
Signal.on("living/light_toggle", () => {
    chandelier.toggle();
});
```

## 📊 5. Сравнение с традиционной архитектурой на базе MQTT

| Характеристика | Традиционный стек (MQTT + Home Assistant) | **FerrumOS Brokerless Fabric** |
| :--- | :--- | :--- |
| **Центральный сервер** | ❌ Обязателен (без него ничего не работает) | 🟢 **Не требуется для прямой работы** |
| **Единая точка отказа** | ❌ Брокер Mosquitto / ОС сервера | 🟢 **Отсутствует (Zero SPOF)** |
| **Задержка выключатель $\rightarrow$ реле** | 300–800 мс (заметный лаг) | ⚡ **< 15–20 мс (мгновенный отклик)** |
| **Поведение при падении Wi-Fi** | ❌ Связь между устройствами потеряна | 🟢 **Thread и CAN продолжают работать** |
| **Масштабируемость проводной сети** | Ограничена портами свитча | 🟢 **До 100+ узлов на одной паре проводов CAN** |
| **Самоисцеление сети** | ❌ Требуется ручной перезапуск сервисов | 🟢 **Аппаратное (Thread / CAN авто-арбитраж)** |
