# RFC 0003: Самовосстанавливающееся обнаружение узлов и сетевой контур WSRPC (Self-Healing Discovery & Embedded WSRPC Provisioning)

| Метаданные | Значение |
|---|---|
| **Номер** | RFC-0003 (консолидирован с RFC-0011) |
| **Статус** | `## Реализовано` (Фаза 1: HTTP Call-Home & UDP Beacon) / `## Планируется` (Фаза 2: Embedded WSRPC & Hardware AEAD) |
| **Целевые платформы** | ESP32-C6 (RISC-V Wi-Fi 6), ESP32-C3 (RISC-V), ESP32-S3, FerrumOS Studio Server (Granian RSGI) |
| **Связанные модули** | `crates/esp32c6-firmware`, `crates/esp32c3-firmware`, `tools/ferrum/web_server/`, `tools/ferrum/fleet.py` |

---

## 🧭 Общая концепция жизненного цикла узла

Сетевая подсистема FerrumOS спроектирована для мгновенного появления плат в сети без ручной настройки IP-адресов, устойчивости к смене адреса сервера и экономного расхода оперативной памяти микроконтроллера:

```text
 ┌───────────────────┐
 │ 1. BOOT & DHCP    │ ─── Чип включается, получает IP-адрес от роутера
 └─────────┬─────────┘
           │
           ▼
 ┌───────────────────┐
 │ 2. DISCOVERY      │ ─── Фаза 1 (Реализовано): HTTP POST /api/discovery/call_home
 └─────────┬─────────┘     Fallback: UDP Broadcast :4242 (who_is_server / server_here)
           │
           ▼
 ┌───────────────────┐
 │ 3. PROVISIONING   │ ─── Сервер регистрирует узел в инвентаре парка и транслирует
 └─────────┬─────────┘     событие в веб-интерфейс Studio (WSRPC: "node.discovered")
           │
           ▼
 ┌───────────────────┐
 │ 4. ACTIVE RUNTIME │ ─── Текущий режим (Реализовано): Pull-поллер сервера раз в 1 сек
 └─────────┬─────────┘     Будущий режим (Планируется): Полнодуплексный сокет Embedded WSRPC
           │
           ▼ (при сбое связи или перезагрузке сервера)
 ┌───────────────────┐
 │ 5. SELF-HEALING   │ ─── Автоматический возврат к Шагу 2 (UDP поиск нового адреса)
 └───────────────────┘
```

## ## Реализовано

### 1. Архитектура онбординга и разделение сетевых контуров

В текущем релизе взаимодействие разделено на два изолированных сетевых контура:

```text
  [ ESP32-C6 / C3 Контроллер ]
         │
         │  1. HTTP POST /api/discovery/call_home (быстрый онбординг ~30 мс)
         │  2. UDP Broadcast :4242 (who_is_server, маяк поиска)
         ▼
  [ FerrumOS Studio Server (Granian RSGI) ]
         │
         │  3. WSRPC (JSON-RPC 2.0 over WebSocket)
         │     - Пуш нового узла: broadcast "node.discovered"
         │     - Стриминг метрик: "telemetry.tick"
         │     - Подтверждение отрисовки: "telemetry.report_ui_state"
         ▼
  [ Браузер Studio (Svelte 5 UI) ]
```

1. **Контур «Контроллер ↔ Сервер» (HTTP POST & UDP Beacon)**:
   - Микроконтроллеры ESP32 со стеком `smoltcp` имеют ограниченный пул сокетов (1 TCP-сокет на 80 порту для внутреннего веб-сервера RWP).
   - При старте чип не держит постоянного соединения: он делает короткий HTTP POST (`POST /api/discovery/call_home`) в первую секунду после получения IP. Запрос занимает ~30 мс и сразу освобождает сокет.
   - **Self-Healing Fallback (UDP 4242)**: Если сервер сменил локальный IP-адрес и не отвечает по HTTP, чип шлёт широковещательный UDP-запрос `who_is_server` на порт 4242. Сервер отвечает пакетом `server_here` со своим новым IP, после чего связь восстанавливается.

2. **Контур «Сервер ↔ Браузер Studio» (WSRPC)**:
   - Все сессии Studio подключены к серверу через WSRPC (JSON-RPC 2.0 over WebSocket).
   - При получении пакета Call-Home сервер мгновенно транслирует событие `node.discovered` во все открытые вкладки Studio без перезагрузки страницы.

### 2. Спецификация сетевых пакетов

#### 2.1. Первичный Call-Home (HTTP POST)
- **URL**: `POST http://<SERVER_IP>:8000/api/discovery/call_home`
- **Заголовки**: `Content-Type: application/json`, `Connection: close`
- **Тело запроса (JSON)**:
  ```json
  {
    "node_id": "c6_16e210",
    "ip": "192.168.1.117",
    "port": 80,
    "board": "esp32c6_supermini",
    "chip": "ESP32-C6",
    "mac": "60:55:f9:16:e2:10",
    "upc": "16e210",
    "firmware_version": "0.6.0",
    "free_heap_kb": 256
  }
  ```
- **Ответ сервера (200 OK)**:
  ```json
  {
    "status": "ok",
    "node_id": "c6_16e210",
    "ip": "192.168.1.117",
    "port": 80,
    "board": "esp32c6_supermini",
    "chip": "ESP32-C6",
    "registered": true,
    "is_new": false,
    "ip_changed": false,
    "server_ip": "192.168.1.109",
    "server_port": 8000,
    "message": "Node successfully synced with FerrumOS Studio"
  }
  ```

#### 2.2. Аварийный поиск сервера (UDP Broadcast 4242)
Используется, когда сохраненный IP сервера недоступен (сервер перенесли или роутер выдал ему другой адрес):
- **Периодический маяк платы**:
  ```json
  {"ferrum": true, "upc": "16e210", "node_id": "c6_16e210", "board": "esp32c6_supermini", "port": 80}
  ```
- **Запрос координат сервера (`who_is_server`)**:
  ```json
  {"ferrum": true, "ask": "who_is_server", "node_id": "c6_16e210"}
  ```
- **Ответ сервера (`server_here`)**:
  ```json
  {"ferrum": true, "response": "server_here", "server_ip": "192.168.1.109", "server_port": 8000, "timestamp": 1725300000}
  ```

#### 2.3. WSRPC-события в Studio Server

| Метод WSRPC | Направление | Назначение |
|---|---|---|
| `node.discovered` | Сервер $\rightarrow$ Studio UI | Мгновенный пуш при появлении нового узла или изменении IP |
| `telemetry.tick` | Сервер $\rightarrow$ Studio UI | Пакетный пуш телеметрии со всех узлов (раз в 1 сек) |
| `telemetry.report_ui_state` | Studio UI $\rightarrow$ Сервер | Подтверждение отрисовки карточки узла на клиенте |

### 3. Механизм защиты от воскрешения удалённых узлов (Tombstone)

Чтобы узлы, намеренно удаленные пользователем из дашборда, не появлялись снова при очередном UDP-маяке, используется реестр «надгробий» (`ignored_nodes`):

```json
{
  "nodes": {
    "c6_16e210": { "ip": "192.168.1.117", "port": 80, "board": "esp32c6_supermini" }
  },
  "ignored_nodes": [
    "c6_191660"
  ]
}
```

1. При клике «Удалить модуль» в Studio узел помечается флагом `is_ignored = 1` в SQLite и заносится в `ignored_nodes`.
2. Обработчики `BeaconListener` (UDP) и `process_call_home` (HTTP) игнорируют пакеты от узлов из чёрного списка и возвращают статус `{"status": "ignored"}`.
3. При повторном ручном добавлении через кнопку «+ Добавить модуль» узел исключается из `ignored_nodes` и возвращается в активный мониторинг.

---

### 4. Текущая модель сбора телеметрии (Серверный Poller)

1. **Параллельный опрос через `asyncio.gather`**:
   - Фоновый воркер сервера (`telemetry_broadcast_loop`) раз в 1 секунду параллельно опрашивает все платы парка по HTTP:
     ```python
     status = await asyncio.to_thread(RwpClient.get_status, ip, rwp_port, timeout=1.2)
     ```
   - Задержка или отключение одной платы не блокирует мониторинг остальных.
2. **Single-Flight кэш памяти (`telemetry_cache`)**:
   - Данные кэшируются на 2.5 секунды. Если несколько пользователей одновременно открыли Studio, плата не бомбардируется параллельными запросами — ответ отдается из памяти сервера.
3. **Обход локальных VPN**:
   - Определение IP сервера (`discovery.get_local_ip()`) отсекает виртуальные туннели (WireGuard, OpenVPN) и привязывается к физическому адаптеру локальной сети.

## ## Планируется

### 1. Фаза 2: Embedded WSRPC — Полнодуплексный сокет на чипе (Event-Driven Edge)

В следующей итерации архитектуры микроконтроллеры переходят с серверного HTTP-опроса на **постоянное исходящее WebSocket-соединение (`ws://<server>:8000/ws/device`)**:

```text
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│                       FERRUMOS EMBEDDED WSRPC LIFECYCLE (PHASE 2)                         │
├───────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                           │
│   [ ESP32-C6 / ESP32-C3 Узел ]                                   [ FerrumOS Studio ]     │
│   ┌───────────────────────────┐   ПОЛНОДУПЛЕКСНЫЙ СОКЕТ WSRPC    ┌──────────────────────┐  │
│   │ • 1 исходящий TCP-клиент  │◄────────────────────────────────►│ • Granian RSGI       │  │
│   │ • RAM: 1KB RX + 1KB TX    │      (Event-Driven, без поллера) │ • rsgi-wsrpc Core    │  │
│   │ • Аппаратный AES-128-GCM  │                                  │ • SQLite ferrum.db   │  │
│   └───────────────────────────┘                                  └──────────────────────┘  │
│                                                                                           │
│   1. Push по изменению (Event-Driven):                                                    │
│      chip -> rpc.call("telemetry.tick", { pin: 2, state: 1 })   [Мгновенно при событии]   │
│                                                                                           │
│   2. Симметричные команды сервера:                                                        │
│      server -> node.call("relay.toggle", { id: 1 })             [Задержка < 1 мс]         │
│                                                                                           │
│   3. Энергосбережение (Modem Sleep):                                                      │
│      Пока пины не меняются, радиомодуль переходит в легкий сон, экономя до 70% питания.  │
│                                                                                           │
│   4. Self-Healing восстановление:                                                         │
│      При обрыве сокета чип пытается переподключиться; при неудаче через 10 сек переходит   │
│      в UDP-поиск (who_is_server) и перепривязывается к новому IP сервера.                 │
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

#### 1.1. Баланс оперативной памяти микроконтроллера (RAM Budget: 2.5 КБ)
Клиентская часть WSRPC на Rust работает в режиме `#![no_std]` со статическими буферами:

| Компонент | Расход RAM | Принцип работы |
|---|---|---|
| **TCP Control Block (`smoltcp`)** | ~250 байт | 1 активный дескриптор исходящего сокета |
| **Кольцевой буфер приёма (RX)** | 1 024 байта | Достаточен для любой RPC-команды сервера |
| **Кольцевой буфер отправки (TX)** | 1 024 байта | Достаточен для фрейма телеметрии |
| **WebSocket-парсер (`ws_client.rs`)** | 0 байт кучи | In-place потоковый разбор заголовков RFC 6455 |
| **Десериализация (`serde_json_core`)**| 0 байт кучи | Парсинг JSON прямо из статического буфера |
| **ИТОГО:** | **~2.5 КБ RAM** | **Полное отсутствие фрагментации динамической памяти** |

### 2. Аппаратная криптография: UID-Derived AEAD (Без оверхеда TLS)

Классический TLS 1.3 (`wss://`) на микроконтроллерах начального уровня неприменим: контекст сессии BearSSL/MbedTLS требует **от 25 до 35 КБ RAM** (до трети всей памяти чипа) и вносит задержку до 800 мс на рукопожатие.

Вместо этого внедряется симметричное аппаратное шифрование **AES-128-GCM**:
1. **Аппаратные криптоускорители чипов**:
   - ESP32-C6 / ESP32-C3 / ESP32-S3 имеют встроенный кремниевый блок AES/SHA. Время шифрования блока — **доли микросекунды (12–15 тактов CPU)** с нулевым расходом оперативной памяти.
2. **Деривация ключей на базе уникального eFuse UID**:
   - Каждый чип имеет заводской MAC/UID, прошитый в кремний:
     $$K_{\text{device}} = \text{HMAC-SHA256}(K_{\text{fleet\_master}}, \text{UID}_{\text{chip}})$$
   - При установке WSRPC-сессии стороны обмениваются нонсами от аппаратного генератора TRNG и выводят эфемерный сессионный ключ:
     $$(K_{\text{session}}, \text{Salt}) = \text{HKDF-SHA256}(K_{\text{device}}, \text{Nonce}_{\text{client}}, \text{Nonce}_{\text{server}})$$
3. **Безопасность**:
   - Взлом одного узла не компрометирует другие платы в сети.
   - Полная защита от повторного воспроизведения пакетов (Replay Attacks) за счет счетчика `nonce_counter`.

### 3. Автоматический конечный автомат самовосстановления (Self-Healing State Machine)

В прошивку микроконтроллера закладывается строгий конечный автомат:

```text
                 ┌────────────────────────┐
                 │      DISCONNECTED      │
                 └───────────┬────────────┘
                             │ (получен IP по DHCP)
                             ▼
                 ┌────────────────────────┐
        ┌───────►│  DISCOVERY (Call-Home) │◄─────────────┐
        │        └───────────┬────────────┘              │
        │                    │ (сервер ответил 200 OK)   │
        │                    ▼                           │
        │        ┌────────────────────────┐              │
        │        │   CONNECTING_WSRPC     │              │
        │        └───────────┬────────────┘              │
        │                    │ (WS Upgrade + Handshake)  │
        │                    ▼                           │
(таймаут > 10 сек        ┌────────────────────────┐      │ (сервер недоступен)
 или сменился IP)        │     AUTHENTICATED      │      │
        │        │      (Event-Driven)    │              │
        │        └───────────┬────────────┘              │
        │                    │                           │
        │ (обрыв сокета)     ▼                           │
        │        ┌────────────────────────┐              │
        └────────┤   RECONNECTING_TCP     ├──────────────┘
                 │  (до 3 попыток, 5 сек) │
                 └────────────────────────┘
```

1. **Нормальный режим**: Плата держит сокет в состоянии `AUTHENTICATED` и передает телеметрию только при событиях на датчиках/пинах.
2. **Мягкий реконнект**: При потере Wi-Fi или сбросе сокета чип делает до 3 попыток переподключения по известному IP сервера.
3. **Глубокое восстановление (Fallback)**: Если сервер не ответил за 10 секунд (например, перезагрузка хоста со сменой IP), плата автоматически возвращается в фазу `DISCOVERY` и отправляет UDP-запрос `who_is_server` на порт 4242 для поиска нового адреса.

### 4. Дополнительные планы расширения сети

1. **Анонсы mDNS / ZeroConf (`_ferrum._tcp.local`)**:
   - Мультикаст-обнаружение сервера в локальной сети как альтернатива UDP-широковещанию для сетей с изолированными широковещательными доменами.
2. **Mesh / Thread Discovery**:
   - Онбординг плат без прямого Wi-Fi подключения через Thread-border-router или распределённую шину CAN (RFC-0001).
3. **Безопасное сопряжение (Pairing Token)**:
   - Поддержка одноразового пин-кода или кнопки сопряжения на плате при первом включении в чужой или публичной локальной сети.
