# Спецификация кроссплатформенного байткода FerrumOS (.rhb) и Host-компилятора

## 1. Архитектурная концепция

В FerrumOS принята двухуровневая модель исполнения:
1. **Host-компилятор на ПК (`ferrum-cli` / Python Toolchain):**
   - Выполняет лексический, синтаксический анализ и оптимизацию Mini-JS скрипта на компьютере разработчика.
   - Проверяет контекстную безопасность (коллизии GPIO и шин между параллельными задачами).
   - Упаковывает скомпилированные опкоды в компактный бинарный контейнер **`.rhb` (FerrumOS Bytecode)** с контрольной суммой CRC16.
2. **Кроссплатформенная микро-ВМ на чипе (Bytecode VM Microkernel):**
   - Размер прошивки микроядра: минимальный (без тяжелых текстовых парсеров).
   - На 100% аппаратно-независима: одинаково работает на ESP32-C6 (RISC-V), ESP32-S3 (Xtensa), STM32/RP2040 (ARM Cortex-M) и ПК-симуляторе.
   - Принимает бинарный пакет `.rhb` по бинарному протоколу RWP или HTTP REST, валидирует CRC16 и мгновенно исполняет в RAM (Zero-Downtime Hot-Swap).

```
┌────────────────────────────────────────────────────────┐
│                      ПК / Host                         │
│  [script.js] ──► [ferrumos compiler]  ──► [script.rhb]  │
└───────────────────────────┬────────────────────────────┘
                            │ Wi-Fi RWP Protocol (TCP:80)
┌───────────────────────────▼────────────────────────────┐
│              ESP32-C6 / Microcontroller                │
│  [RWP Listener] ──► [CRC Check] ──► [Multitasking VM]  │
└────────────────────────────────────────────────────────┘
```

## 2. Формат бинарного контейнера (.rhb)

Каждый скомпилированный файл байткода имеет 8-байтный заголовок:

| Смещение | Поле | Тип | Значение / Описание |
| :--- | :--- | :--- | :--- |
| `0x00..0x03` | **Magic** | `[u8; 4]` | `0x52, 0x48, 0x42, 0x01` (`"RHB\x01"`) |
| `0x04..0x05` | **CRC16** | `u16` (LE) | Контрольная сумма CRC-16/CCITT полезной нагрузки |
| `0x06..0x07` | **Length** | `u16` (LE) | Длина секции инструкций в байтах |
| `0x08..` | **Payload** | `[u8; N]` | Поток инструкций виртуальной машины |

## 3. Набор опкодов виртуальной машины (Instruction Set Architecture)

| Опкод | Название | Аргументы | Описание |
| :--- | :--- | :--- | :--- |
| `0x00` | `OP_NOP` | - | Пустая операция |
| `0x01` | `OP_LOG_STR` | `len: u16, msg: [u8; len]` | Вывод строки в UART лог ядра |
| `0x02` | `OP_BIND_GPIO` | `pin: u8, flags: u8` | Конфигурация схемотехники GPIO (1 байт флагов: Direction, Open-Drain/Push-Pull, Pull-Up/Down, Init level) |
| `0x03` | `OP_GPIO_WRITE` | `pin: u8, val: u8` | Статическая запись в GPIO |
| `0x04` | `OP_GPIO_READ` | `pin: u8` | Чтение уровня с GPIO на стек |
| `0x05` | `OP_DELAY_MS` | `ms: u32 (LE)` | Неблокирующая задержка (переводит задачу в `WaitingDelay`, освобождая CPU) |
| `0x06` | `OP_PUSH_I32` | `val: i32 (LE)` | Поместить 32-битное целое число на стек |
| `0x07` | `OP_POP` | - | Снять верхнее значение со стека |
| `0x08` | `OP_ADD` | - | Сложение `(a + b)` |
| `0x09` | `OP_SUB` | - | Вычитание `(a - b)` |
| `0x0A` | `OP_MUL` | - | Умножение `(a * b)` |
| `0x0B` | `OP_DIV` | - | Деление `(a / b)` с защитой от деления на 0 |
| `0x0C` | `OP_STORE_VAR` | `slot: u8` | Сохранить значение со стека в локальную переменную (0..31) |
| `0x0D` | `OP_LOAD_VAR` | `slot: u8` | Загрузить локальную переменную на стек |
| `0x0E` | `OP_JUMP` | `addr: u32 (LE)` | Безусловный переход по адресу в байткоде |
| `0x0F` | `OP_JUMP_IF_ZERO`| `addr: u32 (LE)` | Переход по адресу, если значение на вершине стека == 0 (false) |
| `0x10` | `OP_EQ` | - | Сравнение `==` (помещает 1 или 0) |
| `0x11` | `OP_NE` | - | Сравнение `!=` |
| `0x12` | `OP_LT` | - | Сравнение `<` |
| `0x13` | `OP_GT` | - | Сравнение `>` |
| `0x14` | `OP_LE` | - | Сравнение `<=` |
| `0x15` | `OP_GE` | - | Сравнение `>=` |
| `0x16` | `OP_JUMP_IF_TRUE`| `addr: u32 (LE)` | Переход по адресу, если значение на вершине стека != 0 (true) |
| `0x17` | `OP_GPIO_WRITE_DYNAMIC`| - | Динамическая запись в GPIO (со стека снимаются `pin` и `level`) |
| `0x18` | `OP_RGB_SET_DYNAMIC` | - | Управление адресным светодиодом WS2812 (`pin, r, g, b` со стека) |
| `0x1A` | `OP_MOD` | - | Остаток от деления `(a % b)` |
| `0x20` | `OP_IPC_SEND` | - | `ipc.send(topic, val)`: отправка значения в именованную FIFO-очередь |
| `0x21` | `OP_IPC_RECV` | - | `ipc.recv(topic)`: чтение значения из FIFO-очереди со снятием |
| `0x22` | `OP_IPC_AVAILABLE` | - | `ipc.available(topic)`: проверка количества непрочитанных сообщений в очереди |
| `0x23` | `OP_STATE_SET` | - | `state.set(key, val)`: запись в глобальный реактивный регистр состояния |
| `0x24` | `OP_STATE_GET` | - | `state.get(key)`: чтение актуального значения из регистра состояния |
| `0x25` | `OP_IPC_PUBLISH` | - | `ipc.publish(topic, val)`: атомарная отправка в FIFO-очередь и сохранение в стейт |
| `0x26` | `OP_IPC_WAIT` | - | `ipc.wait(topic, timeout_ms)`: реактивное ожидание события (Zero-CPU sleep до публикации или таймаута) |
| `0x27` | `OP_MQTT_PUBLISH` | `len: u16, topic: [u8; len]` | `mqtt.publish(topic, val, [qos, retain])`: отправка сообщения в MQTT брокер |
| `0x28` | `OP_MQTT_SUBSCRIBE` | `len: u16, topic: [u8; len]` | `mqtt.subscribe(topic, [qos])`: подписка на топик в брокере |
| `0x29` | `OP_MQTT_WAIT` | `len: u16, topic: [u8; len]` | `mqtt.wait(topic, timeout_ms)`: реактивный Zero-CPU sleep до прихода сообщения из брокера |
| `0x2A` | `OP_MQTT_AVAILABLE` | `len: u16, topic: [u8; len]` | `mqtt.available(topic)`: проверка наличия непрочитанных MQTT сообщений |
| `0x2B` | `OP_MQTT_RECV` | `len: u16, topic: [u8; len]` | `mqtt.recv(topic)`: неблокирующее чтение входящего значения |
| `0x2C` | `OP_MQTT_CONNECTED` | - | `mqtt.connected()`: проверка статуса TCP/MQTT соединения с брокером |
| `0x2D` | `OP_HA_DISCOVERY` | `cfg_len: u16, cfg: [u8; cfg_len], top_len: u16, top: [u8; top_len]` | Автообнаружение сущности в Home Assistant |
| `0xFF` | `OP_HALT` | - | Завершение исполнения задачи |

### Формат битовой маски `flags` для `OP_BIND_GPIO` (1 Байт):

```text
  Бит 7   6   5       4        3   2         1             0
┌───────┬───┬───┬───────────┬─────────┬──────────────┬───────────┐
│   Резерв  │Set│Init Level │  Pull   │ Driver Type  │ Direction │
└───────┴───┴───┴───────────┴─────────┴──────────────┴───────────┘
```

* **Бит 0 (`Direction`)**: `0` = `Input`, `1` = `Output`
* **Бит 1 (`Driver Type`)**: `0` = `Push-Pull` (обычный), `1` = `Open-Drain` (открытый сток)
* **Биты 2..3 (`Pull`)**: `00` = `None / Floating`, `01` = `Pull-Up` (~45k к 3.3V), `10` = `Pull-Down` (~45k к GND)
* **Бит 4 (`Initial Level`)**: `0` = `Low` (0V), `1` = `High` (3.3V)
* **Бит 5 (`Has Initial`)**: `1` = применить начальный уровень сразу при инициализации пина

## 4. Правила именования задач (Task ID)

- Имя задачи (`Task ID`) может содержать **от 1 до 32 байт** UTF-8 символов (`[a-zA-Z0-9_-]`).
- Попытка загрузки задачи с именем длиннее 32 байт блокируется компилятором и валидатором на этапе Pre-Flight.

## 5. Энергонезависимое Flash-хранилище и Auto-Boot (`RHFS\x01`)

FerrumOS поддерживает долговременное сохранение скомпилированных задач во внутренней Flash-памяти чипа для автономного старта задач при включении питания (без сети):

- **Flash Partition Offset**: `0x300000` (3 МБ смещение в NOR Flash).
- **Размер сектора**: 4096 байт (4 КБ).
- **Сигнатура заголовка (Magic)**: `b"RHFS\x01"` (FerrumOS Flash Storage v1).
- **Контрольная сумма**: CRC-16/CCITT по всем сохранённым дескрипторам и байткодам.
- **Таблица дескрипторов**: До 8 задач с полями `Task ID (32 B)`, `autostart (1 B)`, `bytecode_len (2 B)`, `bytecode_offset (4 B)`.
- **Auto-Boot**: На этапе старта ядро считывает заголовок, валидирует CRC16 и автоматически запускает в RAM все задачи, помеченные `autostart == 1`.
