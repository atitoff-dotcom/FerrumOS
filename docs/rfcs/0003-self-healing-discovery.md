# 🧭 Руководство: Self-Healing Call-Home Discovery & Node Provisioning

Этот документ фиксирует архитектуру, спецификацию протоколов и реализованный механизм автоматического обнаружения и привязки модулей **FerrumOS** на базе активного обратного вызова (**Call-Home**) с защитой от смены IP-адресов сервера (**Self-Healing Dynamic Discovery**), параллельным опросом и защитой от зомби-устройств (**Tombstone**).

---

## 🎯 Решенные проблемы

1. **Мгновенный онбординг (1 секунда вместо 30–45 секунд)**:
   Раньше сервер перебирал подсеть брутфорсом (`192.168.1.0/24`) или пассивно ждал долгих таймеров ARP-кэша Windows. Теперь чип сам инициирует HTTP-запрос к серверу в первую же миллисекунду после поднятия Wi-Fi.
2. **Изоляция сбойных и оффлайн-узлов**:
   Опрос узлов переведен на полностью асинхронный параллельный механизм (`asyncio.gather`). Недоступный или выключенный модуль больше не задерживает опрос живых узлов ни на миллисекунду.
3. **Обход VPN-туннелей на хост-машине**:
   Служба обнаружения корректно определяет физический сетевой адаптер домашней локальной сети (`192.168.1.109`), игнорируя виртуальные интерфейсы WireGuard/Amnezia/VPN (`10.251.0.35`).
4. **Устранение коллизий единственного TCP-сокета smoltcp**:
   На микроконтроллере ESP32-C6 выделен один TCP-сокет на 80 порту. Сервер реализует кэширование телеметрии в оперативной памяти (Single-Flight), предотвращая сброс соединений (TCP RST) при одновременных запросах из веб-интерфейса и фонового поллера.
5. **Предотвращение повторного воскрешения удаленных устройств (Tombstone)**:
   При удалении модуля из парка его ID заносится в список игнорирования (`ignored_nodes`). Модуль не возрождается на дашборде самопроизвольно, пока пользователь явно не добавит его заново.

## 🏛️ Архитектура двухуровневого Call-Home

```text
                          Старт контроллера ESP32-C6
                                      │
                                      ▼
                      Подключение к Wi-Fi и получение DHCP (2 сек)
                                      │
                                      ▼
                  Активный HTTP POST /api/discovery/call_home
                                      │
                     ┌────────────────┴────────────────┐
                     ▼                                 ▼
             Сервер ответил 200 OK             Сервер не ответил (сменил IP)
                     │                                 │
                     ▼                                 ▼
            Карточка в Studio ONLINE            Включается Fallback:
            (через 30 миллисекунд!)             UDP-запрос who_is_server (порт 4242)
                                                       │
                                                       ▼
                                                Сервер отвечает чипу:
                                                {"server_ip": "192.168.1.109", "port": 8000}
                                                       │
                                                       ▼
                                                Чип обновляет IP сервера и шлет HTTP Call-Home
```

## 📡 Спецификация сетевых протоколов

### 1. Активный Call-Home (HTTP POST)

- **Эндпоинт**: `POST http://<SERVER_IP>:8000/api/discovery/call_home`
- **Заголовки**: `Content-Type: application/json`, `Connection: close`
- **Тело запроса (JSON)**:
  ```json
  {
    "node_id": "c6_16e210",
    "ip": "192.168.1.117",
    "port": 80,
    "board": "esp32c6_supermini",
    "chip": "ESP32-C6",
    "upc": "16e210",
    "firmware_version": "0.6.0"
  }
  ```
- **Ответ сервера (200 OK)**:
  ```json
  {
    "status": "ok",
    "node_id": "c6_16e210",
    "is_new": false,
    "ip_changed": false
  }
  ```
- **Поведение сервера**:
  - Автоматически создает профиль цифрового двойника в `storage/nodes/<node_id>/device.json`.
  - Регистрирует IP в `tools/fleet.json`.
  - Отправляет WebSocket-уведомление в интерфейс Studio.
  - Если узел находится в `ignored_nodes`, возвращает `{"status": "ignored"}` и не выводит на экран.

---

### 2. Динамический маяк и поиск сервера (UDP Broadcast: 4242)

- **Периодический маяк**:
  Каждые 3.5 секунды контроллер отправляет UDP Broadcast на адрес `255.255.255.255:4242`:
  ```json
  {"ferrum": true, "upc": "16e210", "node_id": "c6_16e210", "board": "esp32c6_supermini", "port": 80}
  ```
- **Запрос координат сервера (`who_is_server`)**:
  Если чип не может связаться с сервером по HTTP:
  ```json
  {"ferrum": true, "ask": "who_is_server", "node_id": "c6_16e210"}
  ```
- **Ответ сервера**:
  ```json
  {"ferrum": true, "response": "server_here", "server_ip": "192.168.1.109", "server_port": 8000, "timestamp": 1725300000}
  ```

## 🛡️ Механизм Tombstone (`ignored_nodes`)

В `tools/fleet.json` поддерживается список удаленных узлов:

```json
{
  "nodes": {
    "c6_16e210": {
      "ip": "192.168.1.117",
      "port": 80,
      "board": "esp32c6_supermini",
      "description": "ESP32-C6 на столе"
    }
  },
  "ignored_nodes": [
    "c6_191660"
  ]
}
```

1. При нажатии «Удалить модуль» узел удаляется из `nodes` и добавляется в `ignored_nodes`.
2. Фоновые службы `BeaconListener` и `routes_discovery` игнорируют сигналы от узлов из черного списка.
3. При явном ручном добавлении через кнопку «+ Добавить модуль» узел автоматически удаляется из `ignored_nodes` и возвращается в рабочий строй.

## ⚡ Оптимизации производительности поллера

1. **Параллелизм `asyncio.gather`**:
   Все узлы парка опрашиваются параллельно в неблокирующих потоках. Таймаут выключенного узла (1.2 с) никак не влияет на опрос активного узла (30 мс).
2. **Сквозное логирование с миллисекундами**:
   Все события записываются одновременно в консоль и в файл `storage/logs/server.log`:
   `[21:43:01.716] [INFO] [Telemetry] Node 'c6_16e210' (192.168.1.117:80) -> ONLINE (32.76ms, Heap: 113KB, RSSI: -65dBm)`
3. **Двусторонняя обратная связь из UI**:
   Браузер при перерисовке статуса отправляет подтверждение `ui_state_change` в WebSocket, позволяя сопоставлять сетевой ответ чипа и момент отрисовки на экране пользователя.
