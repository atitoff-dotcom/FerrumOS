## 🎯 1. Введение и Проблематика

### 1.1. Контекст промышленной автоматизации
В системах автоматизации критической инфраструктуры — **промышленных теплицах, котельных, центрах обработки данных (ЦОД), насосных станциях и непрерывных производственных линиях** — остановка управляющего сервера даже на 10–30 секунд недопустима:
* В тепличном комплексе сбой климат-контроля в мороз приводит к вымерзанию урожая за 20 минут.
* В ЦОД отключение контура охлаждения ведет к перегреву серверных стоек и аварийному отключению оборудования.
* В котельных задержка реакции защиты может привести к гидроударам и авариям котлов.

Классические любительские системы умного дома (Home Assistant, OpenHAB) категорически не подходят для таких задач: у них отсутствует архитектура горячего резерва (Hot Standby), состояние размазано по тысячам динамических объектов Python и тяжелой базе SQLite/Postgres, а время холодного перезапуска после сбоя составляет от 1.5 до 3 минут с гарантированной потерей последних телеметрических точек.

Промышленные решения от вендоров автоматизации (Siemens S7-400H, Schneider Modicon M580 Hot Standby, Beckhoff TwinCAT Redundancy) решают эту задачу, но стоят от **\$8,000 до \$25,000** за контроллерный шкаф и лицензии, требуют прокладки проприетарной оптоволоконной синхро-линии и жестко привязаны к экосистеме одного производителя.

## 🏛️ 2. Архитектурный прорыв FerrumHub: Почему Hot Standby у нас прост и быстр

В FerrumHub реализована плоская, компактная структура памяти **Reactive State Bus**:
1. **Размер всего состояния:** все регистры, датчики и флаги исполнительных механизмов на объекте хранятся в виде плоской карты `u16 -> SignalRecord (val_type: u8, value: i32, timestamp: i64)`.
   * Даже на крупном объекте с **5 000 сигналов** объем памяти State Bus составляет **всего ~80 Килобайт!**
2. **Время синхронизации:** 80 КБ передаются по локальной сети или кросс-кабелю за **0.2 миллисекунды**.
3. **Детерминированность WASM:** состояние песочниц в `wasmi` строго детерминировано, изолировано от хостовых дескрипторов ОС и не зависит от фонового сборщика мусора.

Это позволяет реализовать полноценный **промышленный горячий резерв (Hot Standby 1+1)** с временем перехвата управления **< 50 миллисекунд** без сложной инфраструктуры, используя два недорогих устройства (например, два промышленных контроллера или два ТВ-бокса по \$20).

## 📐 3. Схема отказоустойчивого кластера (1+1 Active-Passive)

```text
               Виртуальный IP (VRRP / GARP): 192.168.1.10
                                   │
                ┌──────────────────┴──────────────────┐
                ▼                                     ▼
     ┌─────────────────────┐               ┌─────────────────────┐
     │    Контроллер #1    │   Heartbeat   │    Контроллер #2    │
     │      [MASTER]       │ ◄───────────► │      [STANDBY]      │
     │  IP: 192.168.1.11   │  Delta-Stream │  IP: 192.168.1.12   │
     │  • Держит VIP       │  (UDP < 1мс)  │  • Теневой режим    │
     │  • Исполняет логику │               │  • Зеркалит Bus     │
     │  • Вещает в шину    │               │  • Готов к старту   │
     └──────────┬──────────┘               └──────────┬──────────┘
                │                                     │
     ═══════════╧══════════════ CAN-шина ═════════════╧════════════ (Общий провод TWAI / CAN)
                                   │
                 ┌─────────────────┼─────────────────┐
                 ▼                 ▼                 ▼
          [Релейный блок]   [Климат-контроль]  [Ввод питания]
```

### 3.1. Роли узлов
* **Master (Основной активный узел):**
  - Привязывает виртуальный IP (например, `192.168.1.10`).
  - Принимает внешние подключения пользователей (Web SPA, WebSocket, REST API).
  - Исполняет реактивные скрипты и таймеры в песочницах WASM.
  - Опрашивает физические шины (CAN/TWAI, Modbus RS485).
  - При любом изменении любого сигнала немедленно формирует сетевой пакет `DeltaSync` и отправляет его по выделенному каналу узлу Standby.
* **Standby (Резервный теневой узел):**
  - Подключен к той же физической CAN-шине и локальной сети.
  - Находится в режиме пассивного слушателя (Silent/Listen-Only mode) для шины управления.
  - Принимает пакеты `DeltaSync` и обновляет свою локальную шину State Bus в оперативной памяти (поддерживая полную идентичность с Master).
  - Слушает Heartbeat-пакеты от Master каждые 10–20 миллисекунд.

## ⚡ 4. Механизм обнаружения сбоев и переключения (Failover)

### 4.1. Двойной канал Heartbeat (Dual-Channel Liveness)
Для исключения ложных переключений из-за локального сбоя одного сетевого интерфейса мониторинг ведется одновременно по двум независимым физическим средам:
1. **Ethernet / IP (Primary Link):** UDP-пакеты Heartbeat каждые 20 мс с контрольной суммой CRC16 и номером последовательности.
2. **CAN / TWAI Bus (Secondary Link):** широковещательный кадр арбитража `CAN ID: 0x0001` каждые 50 мс.

### 4.2. Алгоритм аварийного перехвата (< 50 мс)
1. Если Standby узел фиксирует потерю 3 последовательных Heartbeat-пакетов (прошло 60 мс):
   - Проверяется состояние шины CAN: если на шине CAN активность Master также прекратилась — факт падения Master подтвержден.
2. Standby узел мгновенно переходит в режим **Active Master**:
   - Отправляет Gratuitous ARP (GARP) в локальную сеть, перехватывая виртуальный IP-адрес (`192.168.1.10`) на свой физический MAC-адрес (время обновления таблиц коммутаторов — 1–2 мс).
   - Активирует передатчик CAN-контроллера (перевод из Listen-Only в Normal Mode).
   - Вызывает в WASM-ядре системный хук: `on_cluster_role_changed(ROLE_MASTER)`.
   - Начинает генерацию тактовых импульсов, таймеров и отправку управляющих сигналов.
3. Все браузеры и SCADA-системы, подключенные по WebSocket к виртуальному IP, переподключаются за 1–2 секунды и видят то же самое состояние датчиков без провалов.
4. **Бесшовность для оборудования (Bumpless):** исполнительные реле и приводы на микроконтроллерах FerrumOS не сбрасываются, так как задержка в 50 мс меньше времени отпускания электромагнитных контакторов (обычно 80–120 мс).

## 🛡️ 5. Защита от Split-Brain (Разделения сети)

Классическая проблема кластеров — когда канал связи между узлами оборвался, оба узла живы, оба считают себя Master'ом и начинают слать конфликтующие команды на исполнительные механизмы.

В FerrumHub эта проблема решена на трех уровнях защиты:

### Уровень 1: Аппаратный арбитраж CAN-шины (Физический уровень)
В протоколе CAN/TWAI на физическом уровне витой пары заложен принцип неразрушающего побитового арбитража:
* Доминантный бит (логический 0) всегда перетягивает рецессивный бит (логическую 1).
* Приоритет пакетов задается идентификатором.
* Если оба узла попытаются одновременно послать кадр в CAN-шину, узел с приоритетным ID (Master) продолжит передачу без помех, а второй узел (Standby) аппаратно обнаружит конфликт битов на шине, немедленно прекратит передачу и уйдет в режим ожидания.

### Уровень 2: Узел-свидетель (Witness Node / Кворум 2 из 3)
В распределенных сетях без общей CAN-шины в качестве третьего независимого голоса (Witness) может выступать любой копеечный микроконтроллер FerrumOS (например, ESP32-C3 за \$2, управляющий вводным автоматом щита):
* Узлы запрашивают подтверждение лидерства у Witness-узла через UDP/CoAP.
* Перехват виртуального IP разрешен только тому узлу, который имеет кворум (свой голос + голос Witness).

### Уровень 3: Аппаратный Fencing / STONITH (Shoot The Other Node In The Head)
На ответственных промышленных объектах Standby-контроллер физически подключен к реле питания основного узла (через сухой контакт или управляемый PDU). При подтверждении зависания основного узла Standby аппаратно обесточивает сбойный контроллер, исключая любые паразитные наводки на линии.

## 🔄 6. Обратная синхронизация при восстановлении (Failback)

Когда упавший контроллер Узел 1 починили или перезагрузили:
1. Узел 1 стартует с флагом `--cluster-role auto`.
2. Он видит в сети работающий Узел 2, удерживающий виртуальный IP и шину CAN.
3. Узел 1 **не пытается вернуть себе роль Master силой** (принцип Non-Preemptive Failover предотвращает лишние переключения).
4. Узел 1 отправляет запрос на синхронизацию: `GET /api/cluster/sync`.
5. Узел 2 отдает полный снапшот State Bus (~80 КБ) и архива дельт.
6. Узел 1 встает на дежурство в роли **Standby (Горячий резерв)**.

## 💻 7. Конфигурация в `ferrum-runner`

В микро-гипервизор `ferrum-runner` закладываются следующие флаги запуска и параметры кластера:

```bash
# Запуск основного узла (Узел 1)
ferrum-runner ferrum-hub.wasm \
  --cluster-mode active-passive \
  --cluster-peer 192.168.1.12:8090 \
  --cluster-vip 192.168.1.10/24 \
  --cluster-heartbeat-ms 20 \
  --cluster-priority 100

# Запуск резервного узла (Узел 2)
ferrum-runner ferrum-hub.wasm \
  --cluster-mode active-passive \
  --cluster-peer 192.168.1.11:8090 \
  --cluster-vip 192.168.1.10/24 \
  --cluster-heartbeat-ms 20 \
  --cluster-priority 90
```

### Системный вызов хоста для WASM:
Модули WASM получают доступ к состоянию кластера:
* `ferrum_cluster_get_role() -> i32` (1 = Master, 2 = Standby, 0 = Standalone)
* Хук `on_cluster_role_changed(new_role: i32)` оповещает плагины о переключении для сброса локальных кэшей.
