# Реактивная модель событий

FerrumOS спроектирован вокруг **чистой реактивной модели событий (Reactive Reactor)**.

В устройствах умного дома и автономных батарейных датчиках блокирующие задержки (`delay(1000)` или пустые циклы ожидания) сжигают энергию батареи и блокируют параллельные задачи. FerrumOS заменяет холостые циклы аппаратными прерываниями.

---

## ⚡ Проблема блокирующих задержек (`delay`)

Традиционный подход из мира Arduino и MicroPython:

```javascript
// ❌ Традиционный блокирующий цикл:
while (true) {
    if (readPin(9) == LOW) {
        togglePin(15);
    }
    delay(100); // Процессор молотит на полную мощность в пустом цикле!
}
```

### Почему это плохо:
1. **Быстрый разряд аккумулятора**: Во время `delay()` ядро чипа работает на полной частоте (160 МГц на ESP32-C6), потребляя 25–40 мА.
2. **Пропуск событий**: Пока процессор находится внутри блокирующей паузы, сетевые пакеты или быстрые импульсы могут потеряться.
3. **Хрупкий антидребезг**: Разработчикам приходится городить ненадежные таймеры для фильтрации дребезга контактов.

---

## 🛡️ Реактивная модель FerrumOS

В FerrumOS фильтрация и распознавание событий делегируются аппаратному таймеру и очереди событий ядра:

```javascript
// ✅ Реактивная модель FerrumOS
const btn = GPIO.input(9)
    .pullUp()
    .button()
    .clickMs(350);

const relay = GPIO.output(15)
    .openDrain(false)
    .initial(false);

while (true) {
    // Просыпается ТОЛЬКО когда событие физически распознано
    const gesture = btn.wait();

    if (gesture === Button.CLICK) {
        relay.write(!relay.read());
    }
}
```

### Как это обрабатывает микро-ядро:
1. **Аппаратный сон**: На время вызова `btn.wait()` задача немедленно уступает процессор. RISC-V процессор переходит в режим энергосбережения (`WFI` — Wait For Interrupt).
2. **Нулевая нагрузка на CPU**: Ток потребления падает до микроампер.
3. **Мгновенное пробуждение**: Как только прерывание таймера или фронт сигнала на пине фиксирует завершение жеста, задача просыпается без задержки.
