# Архитектура реактивных сигналов (IPC)

FerrumOS использует архитектуру **реактивной шины сигналов с нулевым копированием (Zero-Copy IPC)** для скоростного и безопасного обмена данными между параллельными скриптами, драйверами и сетью.

---

## ⚡ Проблемы классической многозадачности на микроконтроллерах

В стандартных платформах (FreeRTOS с C++, MicroPython, Arduino):
1. **Борьба за мьютексы и дедлоки**: Разделение общего состояния требует блокировок. При нехватке памяти или сбоях приоритетов чип намертво зависает.
2. **Фрагментация кучи (Heap Thrashing)**: Передача сообщений через динамические очереди приводит к нехватке памяти (OOM) и перезагрузке микроконтроллера.
3. **Холостые циклы опроса**: Опрос флага в цикле `while (flag == 0)` сжигает заряд аккумулятора.

---

## 🛡️ Архитектура шины IPC в ядре FerrumOS

FerrumOS устраняет мьютексы и динамическое выделение памяти с помощью **статической таблицы сигналов**:

```
                  ┌────────────────────────────────────────┐
                  │      Таблица шины сигналов IPC         │
                  │  Слот 0: [ Значение | Версия | Маска ] │
                  │  Слот 1: [ Значение | Версия | Маска ] │
                  │  ...                                   │
                  │  Слот 63:[ Значение | Версия | Маска ] │
                  └───────────────────▲────────────────────┘
                                      │
               ┌──────────────────────┴──────────────────────┐
               │                                             │
      OP_SIGNAL_SET                                  OP_SIGNAL_WAIT
(Источник: инкремент версии)                 (Потребитель: сон WFI до смены версии)
               │                                             │
      ┌────────┴────────┐                           ┌────────┴────────┐
      │  Датчик климата │                           │ Управление реле │
      │   (Скрипт 1)    │                           │   (Скрипт 2)    │
      └─────────────────┘                           └─────────────────┘
```

### 1. Статический массив из 64 слотов
Все сигналы размещены в фиксированной статической таблице памяти ядра. Строковые топики (например, `"living/temp"`) преобразуются в индекс слота с помощью быстрого алгоритма хэширования FNV-1a на этапе компиляции.

### 2. Атомарные переходы с контролем версий
Каждый слот содержит:
- `value: i32` (Целое, вещественное или булево значение);
- `version: u32` (Монотонно растущий счетчик изменений);
- `subscribers_mask: u32` (Битовая маска ожидающих задач).

Когда скрипт записывает значение через `OP_SIGNAL_SET`:
1. Если значение изменилось, версия слота атомарно инкрементируется в критической секции процессора.
2. Ядро проверяет битовую маску `subscribers_mask` и мгновенно переводит ожидающие задачи из статуса `WaitingSignal` в `Runnable`.

### 3. Чистое реактивное ожидание (`OP_SIGNAL_WAIT`)
Когда подписчик вызывает `signal.watch()`, задача исполняет опкод `OP_SIGNAL_WAIT` и немедленно засыпает. Процессор переходит в инструкцию `WFI` (Wait For Interrupt), потребляя микроамперы до момента реального изменения версии сигнала.

## 🌐 Один сигнал — три мира

Главное преимущество сигналов FerrumOS — их абсолютная прозрачность:

```javascript
const motion = state.signal("hall/motion", false)
    .can(15)                                            // Мир 1: Шина CAN (Автоматика / Производство)
    .exposeHA("binary_sensor", { name: "Датчик движения" }); // Мир 2: Home Assistant
                                                        // Мир 3: Локальный скрипт (Реле / LED)
```

1. **Локально**: Скрипты на одном чипе реагируют за доли микросекунды.
2. **Распределенно**: Другие контроллеры на шине CAN принимают кадр по витой паре и обновляют свои зеркала сигналов.
3. **Облако и шлюз**: Home Assistant получает данные по MQTT без ручной правки YAML-файлов.
