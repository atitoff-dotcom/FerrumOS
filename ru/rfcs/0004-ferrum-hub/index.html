    🧭 RFC-0004: FerrumHub — Легковесный сервер оркестрации, микро-гипервизор и WebAssembly-экосистема¶

    Метаданные Значение
    Номер RFC-0004
    Название FerrumHub: Легковесный сервер оркестрации, микро-гипервизор и WebAssembly-экосистема (CAN / Ethernet / Matter / Web)
    Статус Draft / Accepted
    Автор FerrumOS Core Team
    Дата создания 2026-09-05
    Целевые платформы Linux (x86_64, aarch64, armv7), Windows (x86_64), macOS (Apple Silicon / Intel), OpenWrt
    Связанные модули ferrum-runner (микро-хост), ferrum-hub (WASM ядро), ferrum-compiler, rfcs/0001, rfcs/0003

    🎯 1. Введение и Проблематика¶

    1.1. Контекст¶

    Платформа FerrumOS решает задачу детерминированного, быстрого и надежного управления оборудованием на уровне микроконтроллеров (ESP32-C3, ESP32-C6, CH32V307) с использованием безопасного языка Rust, виртуальной машины Rhai/JS и изолированной среды WAMR AOT.

    Однако в комплексных проектах — будь то умный дом, тепличный комплекс, производственный цех, котельная или мониторинг серверных стоек — необходим центральный координатор: * Долгосрочная история телеметрии (графики датчиков, энергопотребления, аварийные логи). * Удаленный доступ и уведомления (Web, PWA, Telegram). * Интеграция фабричных устройств сторонних брендов (через Matter и MQTT). * Календарные расписания, планировщики и астрономические таймеры.

    1.2. Проблемы существующих систем (Home Assistant и др.):¶

    1. Тяжеловесность и зависимость от Python: 1.5–3 ГБ оперативной памяти, долгий холодный старт (1–1.5 мин), паузы на сборку мусора.
    2. Опасные обновления и деградация БД: Постоянные ломающие изменения (Breaking Changes), зависания миграций SQLite, риск окирпичивания сервера при обновлении.
    3. «Суп из сущностей» и YAML-ад: Разделение логики на искусственные «триггеры и условия» с шаблонизатором Jinja2 путает как новичков, так и опытных инженеров и языковые модели (LLM).
    4. Хрупкость плагинов: Ошибка в одной сторонней интеграции способна обрушить весь сервер.

    🏛️ 2. Архитектурный прорыв: Неизменяемый Микро-Хост + WebAssembly-Ядро¶

    Вместо монолитного тяжелого сервера FerrumHub строится на концепции WASM-нативной многозадачной операционной среды:

    💎 3. Ключевые преимущества WASM-архитектуры¶

    3.1. Один файл релиза для всех платформ¶

    • Больше не нужно собирать десятки платформо-зависимых бинарников.
    • ferrum-hub.wasm — единый артефакт. Он абсолютно одинаково исполняется на Windows, Linux x86_64, Raspberry Pi (ARM64), macOS и роутерах OpenWrt.

    3.2. Пользовательские плагины крутятся в том же микро-хосте¶

    • Пользовательские плагины (plugin_xxx.wasm) исполняются рядом с системным ядром под управлением того же микро-раннера.
    • Абсолютная изоляция сбоев: если плагин Modbus разделил на ноль или упал — раннер изолирует ошибку (trap). Ядро ferrum-hub.wasm и другие плагины продолжают работать бесперебойно.
    • Аппаратные квоты ресурсов: раннер жестко ограничивает память (например, 4 МБ) и процессорное время каждого плагина.
    • Сверхбыстрый IPC: обмен данными между плагинами и ядром происходит через разделяемую память за сотни наносекунд без сетевого оверхеда.

    3.3. Неубиваемое обновление и мгновенный откат за 5 мс¶

    • Обновление сервера — это не замена системных файлов в ОС (не требуются права root/admin).
    • Хост загружает ferrum-hub.new.wasm.
    • Если новый модуль успешно стартовал и верифицировал базу данных — он становится активным.
    • Если произошёл сбой — хост за 5 миллисекунд откатывается на ferrum-hub.old.wasm.

    3.4. Транзакционные миграции БД (Zero Corruptions)¶

    • Все миграции схемы БД выполняются внутри строгой ACID-транзакции (BEGIN TRANSACTION ... COMMIT).
    • Перед любой миграцией автоматически создаётся легковесный снимок каталога data/ (5–15 МБ за 0.3 сек).
    • В случае любого сбоя база мгновенно делает ROLLBACK к исходному состоянию.

    🧩 4. Разработка плагинов: Простота и WAMR¶

    4.1. Единый бинарный стандарт — только WAMR / WASM¶

    Разработчики пишут на том, на чём им удобно: * AssemblyScript (TypeScript-синтаксис): код выглядит как привычный TS, компилируется в чистый .wasm. * Rust: строгая типизация и безопасность памяти (wasm32-unknown-none). * C / C++: возможность переиспользовать готовые промышленные библиотеки (BSEC, Modbus, DSP). * Zig / TinyGo: прямая сборка в WebAssembly.

    4.2. Собственный Web UI плагина (Custom Web UI)¶

    Плагин может иметь собственный интерфейс любого уровня сложности: 

    my-awesome-plugin/
├── plugin.wasm        <-- Логика (на AssemblyScript, Rust, C)
└── ui/                <-- Собственный Web UI плагина
    ├── index.html     <-- Любой HTML/JS/CSS или Svelte/React бандл
    └── style.css
    * Безопасный Sandboxed Iframe: веб-интерфейс изолирован (архитектура Figma и VS Code Webviews) и не имеет доступа к системным кукам и авторизации. * Мост window.Ferrum.rpc: фронтенд плагина общается со своим WASM-бэкендом в одну строчку кода.

    4.3. Автогенерация интерфейса настроек (Auto-UI)¶

    Если плагину нужны только параметры конфигурации (токен, порт, интервал) — автор объявляет JSON-схему, а FerrumHub автоматически генерирует модальное окно настроек.

    ⚡ 5. Потоковые реактивные утилиты (DSL Паттерны 1, 2, 3, 4)¶

    В язык скриптов и ВМ внедрены лучшие паттерны потоковой обработки: 1. .deadband(delta) (Фильтр шума / Report-by-Exception): 

    const temp = ADC.sensor(1).deadband(0.2).can("living/temp");
    2. .map(inMin, inMax, outMin, outMax) (Масштабирование диапазонов): 
    const level = ADC.pin(2).map(0, 4095, 0, 100);
    3. .pulse(ms) и .watchdog(ms, callback) (Импульс и Сторож тишины): 
    buzzer.pulse(500); // автовозврат
sensor.watchdog(10000, () => alarm.on()); // защита от засыпания
    4. .throttle(ms) (Rate Limit): 
    pir.throttle(3000).onClick(() => camera.snapshot());

    5.1. Интерактивный граф Code-to-Graph¶

    Компилятор парсит AST кода и автоматически строит интерактивную блок-схему связей в FerrumOS Studio. При живой отладке на плате линии связи пульсируют в реальном времени при прохождении сигналов.

    🤖 6. AI-First & Prompt-Driven разработка¶

    1. Никакой путаницы «триггеры vs условия»: Естественный, интуитивный поток кода: button.onClick(() => { if (isNight) { ... } }).
    2. Системный промпт FERRUM_AI_PROMPT.md: Готовый файл с описанием API и правил Fluent Chaining, позволяющий ChatGPT, Claude или Cursor генерировать 100% валидный код с первой попытки.
    3. Встроенный ИИ-помощник в Studio: Пользователь формулирует задачу словами — Studio генерирует код, а компилятор на TypeScript проверяет его в браузере за < 1 мс.

    🗺️ 7. Дорожная карта реализации FerrumHub (6 этапов)¶

    ┌───────────────────────────────────────────────────────────────────────────────────┐
│                           ПЛАН РАЗРАБОТКИ FERRUMHUB                               │
├─────────────────┬─────────────────────────────────────────────────────────────────┤
│ Этап 1 (Раннер) │ Микро-хост ferrum-runner (Rust) + VTable системных возможностей │
│ Этап 2 (Ядро)   │ ferrum-hub.wasm (Реестр состояний, шина, Matter/MQTT, HTTP API) │
│ Этап 3 (Данные) │ Транзакционные миграции БД + Автобэкапы перед обновлением       │
│ Этап 4 (Плагины)│ WAMR Sandbox для user-плагинов + Sandboxed Web UI (iframe)      │
│ Этап 5 (Дашборд)│ Встроенный PWA Web UI (Svelte 5 / Tailwind)                     │
│ Этап 6 (Релиз)  │ AI-промпты, Studio 1-Click Update, кроссплатформенная дистрибуция│
└─────────────────┴─────────────────────────────────────────────────────────────────┘

    Этап 1: Неизменяемый Микро-Хост (ferrum-runner)¶

    • [ ] Создание крейта crates/ferrum-runner на чистом Rust.
    • [ ] Интеграция WAMR для запуска изолированных WASM-модулей с ограничением ресурсов (RAM, CPU).
    • [ ] Реализация Host VTable (TCP/UDP сокеты, COM/CAN порты, таймеры, файловая система).
    • [ ] Межмодульный Shared-Memory IPC между WASM-инстансами.
    • [ ] Размер бинарника: < 3 МБ, старт: < 10 мс.

    Этап 2: Системное WASM-Ядро (ferrum-hub.wasm)¶

    • [ ] Сборка ядра FerrumHub в целевой формат WebAssembly (ferrum-hub.wasm).
    • [ ] Реактивная шина состояний (State Bus) и обработчик сценариев Modern JS (Rhai).
    • [ ] Интеграция rs-matter (Matter Bridge / Controller) и клиента MQTT.
    • [ ] FeOS Fleet Protocol: опрос и синхронизация микроконтроллеров по CAN и Ethernet.

    Этап 3: Безопасное хранилище и Транзакционные миграции¶

    • [ ] Изолированный каталог data/ с базой данных (SQLite WAL / redb).
    • [ ] Атомарные транзакционные миграции схемы БД (BEGIN TRANSACTION ... COMMIT).
    • [ ] Автоматический моментальный снимок (Snapshot) перед любым обновлением.
    • [ ] A/B горячая замена .wasm модулей с автооткатом за 5 мс.

    Этап 4: Пользовательские WASM-плагины и Custom UI¶

    • [ ] SDK для создания плагинов на AssemblyScript (@ferrumos/plugin-sdk) и Rust.
    • [ ] Поддержка собственной папки ui/ с Sandboxed Iframe.
    • [ ] Двусторонний типизированный RPC-мост window.Ferrum.rpc.
    • [ ] Автогенерация интерфейса настроек (Auto-UI) по JSON-схеме.

    Этап 5: Встроенный Web-интерфейс пользователя (Dashboard PWA)¶

    • [ ] Легковесный адаптивный веб-интерфейс на Svelte 5 / Tailwind.
    • [ ] Визуальный редактор комнат и плиток без редактирования файлов.
    • [ ] Реактивные графики истории телеметрии в реальном времени.

    Этап 6: Интеграция со Studio, AI-Промпты и Релиз¶

    • [ ] Файл FERRUM_AI_PROMPT.md и рецепты автоматизаций для нейросетей.
    • [ ] Интеграция с FerrumOS Studio: обновление сервера и плагинов в один клик.
    • [ ] Публикация единого релиза: ferrum-runner (для всех ОС) + ferrum-hub.wasm.

    📊 8. Сравнение архитектур¶

    Параметр Home Assistant (Python) Node-RED (Node.js) FerrumHub (WASM / Rust)
    Архитектура хоста Монолитный Python процесс Монолитный Node.js V8 Неизменяемый Micro-Hypervisor (Rust)
